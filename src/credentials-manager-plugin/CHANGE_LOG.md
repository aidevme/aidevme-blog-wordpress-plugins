# Credentials Manager Plugin — Change Log

The full version-by-version history of every change made to this plugin, moved out of `SPECIFICATION.md` §10 (which now just points here) to keep that document focused on describing the plugin as it currently is, rather than how it got there.

Every other section of `SPECIFICATION.md` that says "see §10 vNN" is referring to the numbered entry below with that same `vNN` — the numbering here is unchanged from when it lived in the spec, it's simply been relocated.

This is the **ninth** iteration of the underlying spec document. For anyone who saw an earlier version:

- **v1 (custom table + hand-rolled CRUD, no admin UI):** superseded when the URL requirement `/wp-json/wp/v2/credentials` came in — that URL shape is only automatic for a registered post type.
- **v2 (Custom Post Type + native `wp/v2` REST + a classic meta box UI):** delivered the REST URL, but ran into a "critical error" on Publish/Update, most likely from Gutenberg's REST-based save path colliding with the classic meta box's plain-form-POST design. Superseded by dropping the REST/CPT approach entirely: **not** a custom post type, with an admin UX modeled on Contact Form 7 instead.
- **v3 (custom tables, second entity called "Credential Form"):** the working design, just under different names — a `credential_forms` table with a `form_key` column, a `Credpl_Admin_Forms`/`Credpl_Forms_List_Table` admin UI, and a `[credential-form id="…"]` shortcode.
- **v4 renames "Credential Form" to "Credential Block" throughout**, including the parts that matter for already-running sites:
  - **Database**: `Credpl_Installer::maybe_rename_forms_table_to_blocks()` runs before `dbDelta()` in `install()`. If `{$wpdb->prefix}credential_forms` exists and `{$wpdb->prefix}credential_blocks` doesn't yet, it runs `RENAME TABLE … TO …` (preserving every row) and `ALTER TABLE … CHANGE form_key block_key …` to rename that column too. `CREDPL_DB_VERSION` was bumped (`1.0` → `1.1`) specifically to make `maybe_upgrade()` trigger this on sites that already activated an earlier build. If both tables somehow already exist, the migration is skipped rather than risking clobbering data — that scenario isn't expected in normal use.
  - **Shortcode**: `[credential-form id="…"]` → `[credential-block id="…"]`. This is a breaking change for any page/post that already has the old shortcode pasted into its content — WordPress does not alias old shortcode tags to new ones automatically, and this spec doesn't register one. Existing content needs to be found and updated by hand (or via a one-off search-and-replace across `wp_posts.post_content`) after upgrading.
  - **Classes/files**: `Credpl_Admin_Forms` → `Credpl_Admin_Blocks` (`class-credpl-admin-forms.php` → `class-credpl-admin-blocks.php`), `Credpl_Forms_List_Table` → `Credpl_Blocks_List_Table` (`class-credpl-forms-list-table.php` → `class-credpl-blocks-list-table.php`).
  - **`Credpl_Data` methods**: every `*_credential_form*()`/`forms_table()`/`form_key_exists()` method renamed to its `*_credential_block*()`/`blocks_table()`/`block_key_exists()` equivalent (see SPECIFICATION.md §6.6).
  - **Admin menu**: `PAGE_FORMS`/`PAGE_FORM_NEW` → `PAGE_BLOCKS`/`PAGE_BLOCK_NEW`; labels "All Credential Forms"/"Add Credential Form" → "All Credential Blocks"/"Add Credential Block" (§6.1) — the requirement that the top-level menu item still lands on this primary list carries forward unchanged, just pointed at the renamed page.
  - **Front end**: the wrapper CSS class `.credpl-credential-form` → `.credpl-credential-block`, the `data-credpl-form` attribute → `data-credpl-block`, and the stylesheet file `assets/css/credpl-credential-form.css` → `assets/css/credpl-credential-block.css`.
  - **Not renamed**: the Credential (record) edit screen's own `<div id="credpl-credential-form-root">` mount point and its `wp_localize_script` handle `credpl-credential-form`/`credplCredentialForm` — despite containing the word "form," these refer to the HTML `<form>` used to edit a single Credential (§6.2), an unrelated concept to the Credential Block entity being renamed here, and were deliberately left alone.
  - `badge_media`, `credential_link`, `badge_link`, `issuer`, and `title` (on both tables) all carry over conceptually unchanged through every iteration.
  - `tags` (added in v2 to mirror the WP REST Posts schema, then resolved to a real `post_tag` taxonomy relationship) has **no equivalent** from v3 onward — it was entirely a byproduct of aligning with the core Posts REST schema, which no longer applies now that this isn't a post type. Flag if tagging/categorizing credentials is still wanted; it would need its own mechanism.
- **v5 converts both admin React apps from JavaScript to TypeScript** (§6.2.1): `src/index.js` → `src/index.tsx`, `src/credential-block-picker.js` → `src/credential-block-picker.tsx`. Purely a build-time/tooling change — no database, REST, shortcode, or PHP-facing behavior changed; `webpack.config.js`'s entry map, `package.json` (new `typescript`/`@types/react`/`@types/react-dom` devDependencies, new `check-types` script), and a new `tsconfig.json` were the only other files touched.
- **v6 renames the Credential form's source/build files** so the webpack entry key matches its source basename, the same convention the Credential Block picker already followed: `src/index.tsx` → `src/credential.tsx`, and correspondingly `build/index.js`/`build/index.asset.php` → `build/credential.js`/`build/credential.asset.php`. This **is** a real (if small) deployment consideration: `Credpl_Admin_Credentials::enqueue_assets()` now reads `build/credential.asset.php` and enqueues `build/credential.js` — a site running an older build of this plugin (still shipping `build/index.js`) must be updated to the new `dist/credentials-manager-plugin.zip` for the Add/Edit Credential screen to keep loading its script. Nothing about the `wp_localize_script` handle name (`credpl-credential-form`/`credplCredentialForm`) or the mount point (`#credpl-credential-form-root`) changed — those were already correctly named for the *form*, not the file, and were left alone per the v4 note above.
- **v7 absorbs the Credential Block screen's PHP-rendered Title field/`<form>`/Save button into React**, mirroring §6.2's Credential form, and merges the standalone drag-and-drop picker into it as one component tree: `src/credential-block-picker.tsx` (picker-only) is deleted; its component code moves into a new `src/credentials-block.tsx`, which also gains the Title `Field`/`Input` and the `<form>`/hidden-inputs/Save `Button` markup that used to be PHP in `Credpl_Admin_Blocks::render_edit_page()`. Renamed along the way, since these names described "just the picker" and now describe the whole form:
  - **Build output**: `build/credential-block-picker.js`/`build/credential-block-picker.asset.php` → `build/credentials-block.js`/`build/credentials-block.asset.php` — same deployment consideration as v6: an older build's zip won't have these new filenames.
  - **Script handle / localized global**: `credpl-credential-block-picker`/`credplCredentialBlockPicker` → `credpl-credential-block-form`/`credplCredentialBlockForm`, now carrying `id`/`nonce`/`actionUrl`/`title`/`addCredentialUrl` (previously rendered by PHP directly into the `<form>`) alongside the existing `allCredentials`/`selectedIds`.
  - **Mount point**: `#credpl-credential-block-picker-root` → `#credpl-credential-block-form-root`, and it's no longer nested inside a PHP `<form>` — the React component renders its own `<form method="post" action={actionUrl}>` now, same pattern as §6.2.2's Credential form.
  - **Not changed**: `Credpl_Admin_Blocks::save()` — the submitted field names (`title`, `credential_ids[]`, `id`, `_wpnonce`, `action`) are identical to what the old PHP-rendered form sent, so the save handler needed no changes, same as every prior React conversion in this plugin.
- **v8 removes the Badge Link field entirely** — from the Credential form and from `credentials`. Unlike every earlier change, this is the first one to actually **drop** a column rather than add or rename one, which `dbDelta()` cannot do on its own (§4.5): `Credpl_Installer::maybe_drop_badge_link_column()` runs an explicit `ALTER TABLE … DROP COLUMN badge_link` (mirroring the table-rename migration's pattern), gated behind `CREDPL_DB_VERSION` bumping `1.2` → `1.3` so `maybe_upgrade()` runs it once on already-active sites; on a fresh install it's a no-op since `credentials` doesn't exist yet when it runs. Also updated: `credpl-credential-form`/`credplCredentialForm` no longer carries a `badgeLink` field, `Credpl_Admin_Credentials::save()` no longer reads/sanitizes `$_POST['badge_link']`, and `Credpl_Shortcode::render_item()`'s front-end link now uses `credential_link` alone — it previously fell back to `badge_link` when `credential_link` was empty, so a credential that only ever had a Badge Link set (and no Credential Link) will render unlinked after upgrading. `badge_media`/the badge *image* (uploaded via the media library) is a separate field and is unaffected — only the manually-entered badge *URL* is gone.
- **v9 redesigns the shortcode's front-end output** to a vertical stacked list with a small (40px) badge icon, and adds two pieces of information that were collected on the Credential form (§6.2) but never actually shown on the front end: the `title` shortcode attribute — previously parsed but completely unused (per the v8-and-earlier note above, informational only, "mirrors Contact Form 7's `title` attribute") — now renders as a heading when non-empty, and each credential's `earned_on`/`expires_on` now render as an "Expires on … · Earned on …" line (`Credpl_Shortcode::format_earned_expires()`, formatted via `date_i18n()` against the site's `date_format` option). Purely a template/CSS change — no schema, save-handler, or localized-data change, so unlike v6–v8 there's no `CREDPL_DB_VERSION` bump and no rebuilt `.js`/`.asset.php` needed, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`. Sites that already have the shortcode pasted into content don't need to touch it — the existing `title="…"` attribute `build_tag()` always included just starts rendering as a heading once the plugin updates.
- **v10 removes the shortcode's `title` attribute** — the front-end heading now always comes straight from the Credential Block's own stored `title` (§4.2), never from a per-shortcode-instance override. v9 had made the `title` attribute affect rendering but left it independently editable per shortcode instance ("Not re-validated against the stored block title"); in practice that let a page's heading silently drift from the block's admin-facing name if someone hand-edited the pasted tag. `Credpl_Shortcode::render()` no longer declares `title` in its `shortcode_atts()` pairs and passes `$block['title']` straight to `render_html()` instead of `$atts['title']`; `Credpl_Shortcode::build_tag()` now generates `[credential-block id="…"]` with no `title="…"` at all. Purely a template change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`. Sites with the shortcode already pasted into content don't need to touch it — a `title="…"` attribute left over from before the upgrade is simply ignored, and the heading switches to tracking the block's own Title field once the plugin updates; if that stored title has since diverged from what a hand-edited `title="…"` used to show, the front end will start displaying the block's title instead.
- **v11 adds a Credentials Type field to `credentials`** — a `credentials_type varchar(50) NOT NULL DEFAULT ''` column (§4.1) holding one of a fixed set of values (`Applied Skills`, `Certifications`, `Awards` — `Credpl_Admin_Credentials::CREDENTIALS_TYPES`), chosen via a Fluent UI `Dropdown` on the Add/Edit Credential form (§6.2) placed immediately after Title. Same category of change as v2's `credential_id`/`certification_number`/etc. additions above: `dbDelta()` adds the new column automatically, so this only needed `CREDPL_DB_VERSION` bumping `1.3` → `1.4` (no explicit migration step) plus the corresponding addition to `Credpl_Installer::missing_credential_columns()`'s expected-columns list. Unlike a free-text field, the value is constrained server-side: `Credpl_Admin_Credentials::sanitize_credentials_type()` checks the submitted value against `CREDENTIALS_TYPES` and stores `''` for anything outside it (a raw POST could submit any string regardless of what the Dropdown client-side offered) — the same allow-list is passed to the React form as `credentialsTypeOptions` (via `wp_localize_script()`) so the Dropdown's own options and the server's validation can't drift apart. Fluent UI 9's `Dropdown` renders a custom listbox rather than a native `<select>`, so — like `DatePicker` before it — it's paired with a hidden `<input type="hidden" name="credentials_type" value={ credentialsType } />` to actually carry the value through the plain form POST. Also shown as a new **Type** column on the Credentials list table (§6.2, immediately after Title — see §6.2 for the table's current column order, which has since been extended and reordered further), rendering `—` for credentials saved before this field existed (or left unset). Not currently surfaced on the front end (the `[credential-block]` shortcode's per-credential output, §7) — extending that to display it would be a separate follow-up if wanted.
- **v12 stops rendering `issuer` in the `[credential-block]` shortcode's front-end output** — `Credpl_Shortcode::render_item()` no longer outputs the `<p class="credpl-credential-issuer">` line, and the now-unused `.credpl-credential-issuer` CSS rule is removed from `credpl-credential-block.css`. `issuer` is still collected on the Credentials form and still shown in its own Credentials list table column (§6.2) — this only affects the public-facing shortcode output. Purely a template/CSS change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v13 shrinks the shortcode's per-credential title text** — `.credpl-credential-title`'s `font-size` in `credpl-credential-block.css` changed from `1em` (i.e. the same size as surrounding body text) to `0.9em`, so it reads a bit smaller than a theme's default paragraph text rather than matching it exactly. Purely a CSS change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`. As with every other rule in this stylesheet, the selector stays deliberately low-specificity, so a theme's own more specific heading styles can still override this value.
- **v14 adds a Description field to `credential_blocks`** — a `description text` column (§4.2), mirroring `credentials.description` (§4.1) added back in v2. Same category of change as v2/v11: `dbDelta()` adds the new column automatically, so this only needed `CREDPL_DB_VERSION` bumping `1.4` → `1.5` (no explicit migration step, and — unlike `credentials` — `credential_blocks` has no `missing_credential_columns()`-style ALTER-privilege detection, so a failed automatic `ALTER TABLE` on this table would surface as a raw DB error on save rather than the friendly admin notice). Shown as a Fluent UI `Field`/`Textarea` on the Add/Edit Credential Block form (§6.3.1), placed right after Title and before the Credentials picker; `Textarea` forwards a plain `name="description"` straight through to its native `<textarea>` (same as `Input`), so — unlike `Dropdown`/`DatePicker` elsewhere in this plugin — it needs no paired hidden input to submit through the plain form POST. Sanitized server-side with `sanitize_textarea_field()` (§8), same as `credentials.description`. Also shown as a new **Description** column on the Credential Blocks list table (§6.3, after Shortcode), rendering `—` when not set. Admin-only: not currently rendered in the `[credential-block]` shortcode's front-end output (§7) — extending that to show it would be a separate follow-up if wanted.
- **v15 adds a Description column to the Credentials list table** (§6.2), at the end, after Badge — rendering `—` when not set. `credentials.description` has existed since v2 and was already collected on the Add/Edit Credential form (a `Field`/`Textarea`, §6.2), just never shown in the list; this only touches `Credpl_Credentials_List_Table`. Purely a PHP/list-table change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump and no rebuilt `.js`/`.asset.php` needed, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v16 makes the Credentials list table's Title, Type, Issuer, Earned On, and Expires On columns sortable** — `Credpl_Credentials_List_Table::get_sortable_columns()` (standard `WP_List_Table` mechanism) marks those five column headers clickable; `prepare_items()` reads `$_GET['orderby']`/`$_GET['order']` (each `sanitize_key()`'d) and passes them to `Credpl_Data::get_credentials()`, whose existing `$orderby`/`$order` allowlist (in place since the very first version of this table, previously just `id`/`title`/`issuer`/`created_at`) is extended to also accept `credentials_type`, `earned_on`, `expires_on` — anything outside that allowlist still falls back to `title`/`ASC`, same as before (§8). Badge and Description are intentionally left out of `get_sortable_columns()` — a media attachment ID and free-text notes aren't meaningful to sort by. Purely a PHP/list-table change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump and no rebuilt `.js`/`.asset.php` needed, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v17 adds a Status field to `credentials`** — a `status varchar(20) NOT NULL DEFAULT ''` column (§4.1) holding one of a fixed set of values (`Active`, `Expired` — `Credpl_Admin_Credentials::STATUSES`), chosen via a Fluent UI `Dropdown` on the Add/Edit Credential form (§6.2), placed right after Credentials Type. Exactly the same pattern as v11's Credentials Type field: `dbDelta()` adds the column automatically, so this only needed `CREDPL_DB_VERSION` bumping `1.5` → `1.6` plus the corresponding addition to `Credpl_Installer::missing_credential_columns()`'s expected-columns list; the value is constrained server-side (`Credpl_Admin_Credentials::sanitize_status()`, values outside `STATUSES` stored as `''`) with the same allow-list passed to the React form as `statusOptions` so the Dropdown's own options and the server's validation can't drift apart; and, like `credentials_type`/`Dropdown` elsewhere in this plugin, it's paired with a hidden `<input type="hidden" name="status" value={ status } />` since Fluent UI's `Dropdown` isn't a native `<select>`. Deliberately a manual field, not derived from `expires_on` — a credential's `status` is whatever the admin sets it to on the form, independent of whether `expires_on` has actually passed. Not currently surfaced in the `[credential-block]` shortcode's front-end output (§7) — extending that to show it would be a separate follow-up if wanted.
- **v18 adds a Status column to the Credentials list table** (§6.2), after Expires On, before Badge — rendering `—` when not set. Not made sortable (unlike Title/Type/Issuer/Earned On/Expires On, §6.2) — not requested, and `credentials_type` already establishes the pattern for a sortable dropdown-backed column if wanted later. Purely a PHP/list-table change — no schema, save-handler, or localized-data change, so no `CREDPL_DB_VERSION` bump and no rebuilt `.js`/`.asset.php` needed, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v19 adds a third table, `{$wpdb->prefix}microsoft_certifications`, with its own full admin screen** (§4.3, §6.4) — a standalone reference table of Microsoft Learn certification catalog entries (`uid`, `title`, `subtitle`, `url`, `icon_url`, `last_modified`, `type`, `certification_type`, `exams`, `levels`, `roles`, `study_guide`), with no relationship to `credentials`/`credential_blocks` (§3). `Credpl_Installer::install()` creates it via `dbDelta()` alongside the other two tables, gated behind `CREDPL_DB_VERSION` bumping `1.6` → `1.7`; unlike `credentials`, it gets no `missing_credential_columns()`-style ALTER-privilege detection, matching `credential_blocks`'s (not `credentials`') level of safety-checking. New classes mirror the existing per-table architecture: `Credpl_Ms_Certifications_List_Table` (list, sortable Title/Certification Type/Type/Last Modified) and `Credpl_Admin_Ms_Certifications` (page callbacks, save/delete — `credpl_save_ms_certification`/`credpl_delete_ms_certification`), plus a third `Credpl_Data` section (`get_ms_certifications()`/`get_ms_certification()`/`insert_ms_certification()`/`update_ms_certification()`/`delete_ms_certification()`/`ms_certification_uid_exists()`). A third React entry, `src/ms-certification.tsx` (webpack multi-entry map extended accordingly, `build/ms-certification.js`/`.asset.php`), needed no new npm dependencies — every field is a plain Fluent UI `Input`/`Textarea` (no `Dropdown`, no `DatePicker`, no hidden-input pairing anywhere on this form, unlike the other two), including a native `<input type="datetime-local">` for `last_modified` and newline-per-item Textareas for `exams`/`levels`/`roles` (JSON arrays, parsed server-side — §6.4 for the full field-by-field rundown). Two new submenu items (**All Microsoft Certifications**, **Add Microsoft Certification**) bring the top-level menu from five to seven items (§6.1). Not exposed via the `[credential-block]` shortcode or anywhere else on the front end (§3, §7) — admin-only, by design.
- **v20 adds a "Sync Certifications" action to the Microsoft Certifications list screen** (§6.4) — a nonce-protected `page-title-action` link (`admin-post.php?action=credpl_sync_ms_certifications` → `Credpl_Admin_Ms_Certifications::sync()`, gated behind a JS `confirm()`, same "nonce-protected `<a>` link" pattern already used for row-level Delete) that fetches `CATALOG_API_URL` (`https://learn.microsoft.com/api/catalog/?type=certifications,exams&locale=en-us`, a fixed constant — no SSRF surface) via `wp_remote_get()` and upserts one row per returned certification, matched by `uid` (`Credpl_Data::get_ms_certification_by_uid()`, new). Every field from the API response is sanitized through the same field-by-field rules `save()` already applies to `$_POST` (`map_catalog_certification()` — reusing `sanitize_string_list()`/`sanitize_json_field()`/etc., §8), with one addition: `sanitize_iso8601_to_mysql()` converts the API's timezone-aware `last_modified` (e.g. `2025-02-05T01:17:00+00:00`) to UTC via a Unix timestamp, unlike the form's own `sanitize_datetime()`, which has no offset to convert in the first place. Redirects back with `synced=1` plus `sync_created`/`sync_updated`/`sync_skipped` counts — prefixed `sync_` specifically so they can't collide with the plain `updated`/`deleted` query-arg flags `save()`/`delete()` already use on redirects to this same screen (an early version of this without the prefix meant a sync that updated exactly one row also triggered the unrelated single-row "Microsoft Certification saved." notice). A single synchronous request/response cycle — no AJAX, no cron/background job — with a best-effort `set_time_limit( 120 )` (suppressed, gated behind `function_exists()`) given the catalog's size; acceptable since this is a manually-triggered, infrequent, admin-only action, not a page load. Purely additive — no schema change, no `CREDPL_DB_VERSION` bump, no rebuilt `.js`/`.asset.php` (React form unaffected), just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v21 makes sync() skips diagnosable** — the very first real-world sync run (on a site with a prior history of restricted database privileges, v6/v14) returned "0 created, 0 updated, 151 skipped" with no way to tell why, since v20's loop only counted skips without recording a reason. `sync()` now tracks the reason for the *first* skip it hits (one of: an entry that wasn't a valid object, an entry with no `uid`, or the actual database error message from a failed `insert_ms_certification()`/`update_ms_certification()` call) and stashes it via the same transient `store_error_notice()` already uses for save() errors; `maybe_render_notice()` appends it to the sync summary as **"First reason: …"** whenever `sync_skipped > 0`. A uniform 100%-skipped result like the one above most likely means `{$wpdb->prefix}microsoft_certifications` itself doesn't exist yet on that site — `dbDelta()` creating it can fail exactly as silently as the `ALTER TABLE`s described in §5/v6, and unlike `credentials`, this table has no `missing_credential_columns()`-equivalent check to catch that and warn about it (a known gap noted when the table was added, v19) — reactivating the plugin re-runs `Credpl_Installer::install()` unconditionally and would create the table if that's the cause. Purely a diagnostics change — no schema, save-handler behavior, or localized-data change, so no `CREDPL_DB_VERSION` bump and no rebuilt `.js`/`.asset.php` needed, just the plugin version bump and a fresh `dist/credentials-manager-plugin.zip`.
- **v22 adds a fourth table, `{$wpdb->prefix}microsoft_exams`, with its own full admin screen** (§4.4, §6.5) — a sibling reference table to `microsoft_certifications` (v19) for individual Microsoft Learn exam catalog entries (`uid`, `title`, `subtitle`, `display_name`, `url`, `icon_url`, `locales`, `last_modified`, `type`, `courses`, `levels`, `roles`, `products`, `providers`, `study_guide`). Same "standalone, no enforced relationship" status as Microsoft Certifications (§3) — a certification's `exams` array (§4.3) names exam `uid`s that correspond to rows here, but nothing validates or links them. `Credpl_Installer::install()` creates it via `dbDelta()` alongside the other three tables, gated behind `CREDPL_DB_VERSION` bumping `1.7` → `1.8`; same level of safety-checking as `microsoft_certifications`/`credential_blocks` (no `missing_credential_columns()`-equivalent). New classes mirror the existing per-table architecture exactly: `Credpl_Ms_Exams_List_Table` (list, sortable Title/Display Name/Type/Last Modified) and `Credpl_Admin_Ms_Exams` (page callbacks, save/delete — `credpl_save_ms_exam`/`credpl_delete_ms_exam` — no Sync action yet at this point, see v23), plus a fourth `Credpl_Data` section (`get_ms_exams()`/`get_ms_exam()`/`get_ms_exam_by_uid()`/`insert_ms_exam()`/`update_ms_exam()`/`delete_ms_exam()`/`ms_exam_uid_exists()`). A fourth React entry, `src/ms-exam.tsx` (webpack multi-entry map extended accordingly, `build/ms-exam.js`/`.asset.php`, styles in `src/styles/msExam.styles.ts`), needed no new npm dependencies — same plain `Input`/`Textarea`-only form as Microsoft Certifications, including a native `<input type="datetime-local">` for `last_modified` and newline-per-item Textareas for the six array fields (`locales`/`courses`/`levels`/`roles`/`products`/`providers`). Two new submenu items (**All Microsoft Exams**, **Add Microsoft Exam**) bring the top-level menu from seven to nine items (§6.1).
